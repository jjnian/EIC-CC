本体血缘图（TBox Lineage Graph）构建完整方案

本文基于对当前代码库的整体盘点，梳理「本体血缘图」从供血源→抽取建图→合并校验→落库版本→数据绑定→下游推演的完整链路，给出每一环的规范、算法、护栏与 API，并在末尾给出差距分析与增强路线图。目标是「尽量全」：既是现状说明书，也是可执行蓝图。

关键实现锚点：ExperienceOntologyService · ExtractionLlmService · ExtractionGraphMerger · GraphSchema · ExtractPrompts · EdgeSemantics · LineageTraversalService · OntologyModelService · NodeBindingController · ExplorationAgentService。

1 · 总览与设计原则

本体血缘图是一张业务语义层的有向图（TBox / 概念级），节点是业务概念（实体/事件/规则/流程/数据/外部系统），边是受控的语义关系（产出/派生/触发/治理/组成…）。它统一承载「这个业务由哪些对象构成、它们如何相互派生与影响」，并作为下游推演（what-if）、血缘追溯、数据资产盘点的底座。

① 证据接地

每个 derived 节点/边必须带 evidence（≤30 字原文摘录）与校准过的 confidence；推断项 inferred 低置信、限额、且只能连接已命名节点。杜绝「常识幻觉」。

② 概念优先于物理

节点是业务概念而非物理表镜像；多张紧密相关表可折叠成一个语义节点，物理痕迹保留在 derived_tables / 属性的 column 里，实现「表级图 + 列级血缘」。

③ 多源汇聚·按 label 归一

文档、schema、对话、经验库、探索五路供血汇入同一 Schema，跨来源/跨切片按规范化 label + aliases 去重合并，同一概念只留一个节点。

④ 语义化血缘方向

边的存储方向 from→to 与「数据流上下游」并不总一致；derived_from/composed_of 是反向。遍历一律按 EdgeSemantics 解析真实数据流。

⑤ 版本化·工作空间隔离

每次保存自动快照（保留 100 份、可按时间戳回滚）；所有仓储按 WorkspaceContext 隔离，模型、绑定、版本互不串号。

⑥ 建图与供血解耦

数据源结构先沉淀成经验参与建图；建好的图节点再反向绑定真实数据来源取数供血。建图（语义）与取数（实例）两阶段分离。

2 · 总体架构与数据流

整体是一条「多源 → 统一抽取 → 合并校验 → 落库版本 → 绑定供血 → 下游消费」的单向管线，全程 SSE 流式上报进度、可中断。

左侧五路供血在 ② 统一进入抽取；结构化「探索图片段」走旁路，直接进入 ③ 合并（免二次 LLM 抽取）。④ 落库后，⑤ 为节点绑定真实数据来源、⑥ 供推演与血缘分析消费。

建图输入并非单一来源，而是五条互补通道，覆盖「非结构化文档 / 结构化 schema / 人在环交互 / 存量经验 / 系统自动探索」。

4 · 本体 Schema 规范

所有通道输出同一 JSON 形状（GraphSchema.SCHEMA_STRING），这是全系统的「通用语」。核心是 add_nodes / add_edges（外加 reply / questions）。

4.1 节点字段字典

字段必填取值 / 说明
id✔局部唯一（如 n_1/t_orders）；服务端会加 chunk 前缀 + 盐避免碰撞。
label✔规范业务概念名（挑一个首选形态）。是跨来源去重的主键。
aliases[]—同义/缩写（['采购单','PO']），用于跨切片、跨来源归并。
type✔entity event rule process data external
source✔derived（原文明述） / inferred（世界知识补全）
evidence✔(derived)≤30 字原文摘录；纯推断为空串。
confidence✔0–1。derived ≈ 0.85–1.0，inferred ≤ 0.55。
derived_tables[]schema 时✔支撑该概念的真实表名（可多表折叠一个概念）。表级图 ↔ 物理血缘的锚。
attributes[]建议{name(业务名), column(物理列), valueSpace, description, source}。列不建节点，落为属性。
props[]—{key,value,source} 自由键值补注。
constraints[]建议{kind, note, source}；kind ∈ cardinality/exclusive/symmetric/transitive/custom。

4.2 边字段字典

字段必填取值 / 说明
id / from / to✔from/to 必须指向 add_nodes 或「已知实体清单」里存在的 id——禁止悬空边/自环。
rel_type✔受控词表（见第 5 节），兜底才用 associated_with。
label✔原文中该关系的具体措辞（展示用，自由文本），如「审批通过后生成」。与 rel_type 分离。
source/evidence/confidence✔同节点规则。
derived_tables[]schema 时✔支撑该关系的表（FK 两表或 N:M 中间表）。
rule_driven✔该关系是否由某规则治理；true 时应同时产出 rule 节点 + governs 边。
constraints[]建议边级约束，如「1:N 一个供应商供多个零件」「symmetric」。
schema 通道的确定性 id：节点 t_<sanitized_table>、边 e_fk_<child>_<col>__<parent>——保证「同一 schema 永远产出同一张图」，便于增量重建与 diff。

5 · 关系语义受控词表

关系类型是一个封闭词表——这既是血缘方向判定的依据，也是下游推演区分「因果 vs 组成 vs 治理」的关键。

rel_type含义存储方向血缘数据流
producesA 产出/生成 B（下游血缘）A→BA → B（正向）
consumesA 消耗/输入 BA→BA → B
derived_fromA 派生自/血缘来源是 B（上游）A→BB → A（反向）
depends_onA 依赖 B 才成立A→BA → B
triggersA 触发 B 发生A→BA → B
governs规则 A 治理/约束 BA→BA → B
composed_ofA 由 B 组成/包含 BA→BB → A（反向）
transformsA 被转换为 BA→BA → B
flows_to数据/物料从 A 流向 BA→BA → B
associated_with兜底（其它都不贴切时）A→BA → B
EdgeSemantics.REVERSED = {derived_from, composed_of}：这两类存储方向与真实数据流相反（来源在 to 端）。任何血缘遍历/上下游分析都必须调 EdgeSemantics.sourceTarget(from,to,rel_type) 拿到真实 [上游源,下游]，不能一律按 from→to。

6 · 抽取合并流水线

把「多次 LLM 抽取的碎片」拼成「一张干净的图」，是 ExtractionGraphMerger（纯函数、无副作用）+ ExtractionLlmService（编排）+ IdSaltRewriter 的联合工作。

Step 1 · 切片 chunkText

长文按 30k 字符切，但优先在换行/句号自然边界断（搜索窗 [max/2, max]），避免把句子/实体从中间切断。

Step 2 · 已知实体回灌

knownEntitiesPreface 把前面切片已识别的节点（id+label+aliases，最多 80 个）回灌给下一片，让本片的边能直接连到「别片的实体」，避免血缘链在切片边界断裂。

Step 3 · id 前缀

prefixChunkIds 给每片 id 加 c0_/b0_/ex0_ 前缀并同步重写边 from/to，避免各片都叫 n1 造成冲突。

Step 4 · 按 label 归并

mergeExtractionByLabel：规范化 label（trim+小写+空白合一）+ aliases 做等价键；命中则合并 props/aliases 并把重复 id 重映射到已存在节点，边随之改指。

Step 5 · 图校验 sanitize

sanitizeGraph：① 丢空 id/重复 id 节点；② 丢 from/to 指向不存在节点的悬空边；③ 丢自环；④ 按 from→to#rel 去重复边。

Step 6 · 加盐 import

IdSaltRewriter.applyImportSalt 给整张图 id 加时间戳盐，避免与已有模型/多次导入撞 id；前端 import 流程据此安全合并。

6.1 经验库整库的并行编排

7 · 质量护栏与反幻觉

「宁缺毋滥（Missing > wrong）」是全系统一致的质量哲学，体现在 prompt 硬约束 + 后处理校验双保险。

文档抽取护栏（H1–H8）

  • H1 每个 derived 节点必须有原文 ≤30 字逐字引用，引不出即非 derived。
  • H2 不加原文未提及的「常识实体」（讲采购不无端加「客户」）。
  • H3/H4/H5 不臆造属性/约束/规则节点。
  • H6 inferred 节点 ≤30%，且只能连接已命名 derived 节点。
  • H7 置信度校准：derived ≥0.85，inferred ≤0.55。
  • H8 少而精优于多而虚（5 个准确节点 > 30 个半编造）。

Schema→本体护栏

  • schema 是唯一真相；无法追溯到 TABLE/COL/FK 的一律视为幻觉、后处理删除。
  • 不臆造列（不给每表加 created_at）、不臆造边（无 FK 不连 triggers）。
  • Rule 4 推断血缘默认关闭，仅当命名严格等于 <parent>_id/_code/_no 且父表存在、无正式 FK 等 5 条件全满足才发一条，置信 0.4。
  • 确定性 id + 无 clarifying question（结构化输入无歧义）。

后处理保险（与 prompt 无关，代码强制）

sanitizeGraph 兜底删除悬空边/自环/重复边/空重 id 节点；mergeExtractionByLabel 强制同概念单节点。即使 LLM 违规，图仍是「干净」的。

8 · 血缘语义与遍历

LineageTraversalService.traverse(modelId, nodeId, dir, maxDepth) 从某节点出发做 BFS，但邻接表按真实数据流方向建，而非存储方向。

  • DOWNSTREAM：沿「上游源 → 下游」，找该节点的所有被派生/被影响方。
  • UPSTREAM：反向，找所有上游来源。
  • 每条边先经 EdgeSemantics.sourceTarget 归一成 [src,tgt]，再据 dir 决定 key/neighbor。
  • 返回 {root, direction, maxDepth, nodes:[{id,label,depth}], edges:[经过的边含 rel_type/evidence]}，供前端画上/下游子图与深度分层。
// 关键：邻接表按血缘方向而非 from→to
for e in edges:
    [src,tgt] = EdgeSemantics.sourceTarget(e.from, e.to, e.rel_type)   // derived_from/composed_of 会翻转
    key      = (dir==DOWNSTREAM) ? src : tgt
    neighbor = (dir==DOWNSTREAM) ? tgt : src
    adj[key] += (neighbor, e)
BFS(nodeId) 直到 depth==maxDepth（≤0 不限）

9 · 落库 · 版本 · 工作空间隔离

模型与存储

OntologyModel = {id,name,nodes,edges,…}，经 MyBatis 落到 ontology_node / ontology_edge / ontology_node_prop 系列表。前端建好的图通过 import 合并进模型后 saveOntology。

版本快照

OntologyModelService.save 每次保存前先把旧版本写入 ontology_model_version*（最多保留 100 份）。listVersions 只返回时间戳 + 节点/边数概要 + 大小；restoreVersion 按时间戳回滚，且回滚本身也会被快照——可撤销的撤销。

工作空间隔离

所有仓储按 WorkspaceContext ThreadLocal 隔离。版本表只按 modelId 过滤，故 requireOwnedModel 先校验归属，防 IDOR 越权查看/恢复他人快照。异步线程需手动透传 workspaceId。

种子数据

空工作空间首次 list 时自动播种 3 个示例图谱，降低上手门槛。

10 · 数据源供血绑定（第二阶段）

图建好后，节点从「概念」落到「实例」：NodeBindingController 把节点绑定到某数据源的表/列。

端点作用
POST /api/node-bindings建绑定 {modelId,nodeId,dataSourceId,tableName,columnMap,filterSql}——节点↔表/列映射。
PUT /api/node-bindings/{id}改绑定（换源/换表/改列映射/改过滤）。
POST /api/node-bindings/{id}/fetch按绑定只读取数：无 filter 走表预览；有 filter 走 SELECT * WHERE filter（连接器强制只读 + LIMIT 兜底），返回 {columns,rows,rowCount,truncated}。
GET /api/node-bindings?modelId&nodeId列出某模型/节点的绑定。
语义层（图）稳定不变，实例层（绑定）可随数据源演化。同一节点可绑多源，为「跨系统同概念对账」留出口。

11 · 下游消费

推演 / What-if（Scenario）

PredictionOrchestrator + PredictLlmService + PredictPromptBuilder：以图为底座做因果推演。输入 seeds（种子事件）、约束（block/probability/force 三模式，probability 走贝叶斯先验更新）、规则（type=rule 单列优先）。大图先经 truncateGraphForContext 裁成「以 seeds/rules 为中心的 N-hop 邻域」。产物落 Scenario（节点解释/边/约束/链路步骤）。

血缘 / 路径 / 图分析

前端分析面板 GraphStatsTab（度/连通/类型分布）、NodeAnalysisTab（单节点供血/上下游）、PathQueryTab（两点路径）。配套 composable：useLineageTrace / useGraphStats / useNodeColoring / useGraphSearch。

对话建模上下文

chat 把「图摘要 + RAG 经验召回 + DB schema + @mention」拼进 prompt，既能问答也能增量改图，形成「边聊边建」闭环。

模板库

/api/templates 存/取图谱模板，跨工作空间复用建模范式。

13 · 端到端操作 SOP（推荐建图路径）

把一个业务系统「建成一张尽量全的血缘图」，推荐如下顺序——先铺语义、再落实例、后验证。

1
供血汇聚。 数据库 → from-ddl 入经验；制度/流程文档 → extract；线上后台 → explore 自动探索（产结构化图片段）。让当前工作空间的经验库尽量覆盖「结构 + 制度 + 界面」三视角。
2
整库建图。 跑 extract-ontology，可加 userHint（如「重点审批链路」）。并行分批 + 结构化直采，得到首版 {nodes,edges}。
3
人在环精修。 前端 import 合并进模型；用 chat 增量补边/补规则、回答澄清 questions；按 confidence/source 着色审查 inferred 项。
4
落库存版。 saveOntology（自动快照）。后续每次大改都有回溯点。
5
绑定供血。 对关键节点建 node-binding（表/列/filter），fetch 验证取数正确。
6
验证消费。 用 lineage 抽查上下游是否符合业务直觉；跑推演验证规则/约束生效；用图分析看孤点/断链，回到 Step 1 补供血迭代。

14 · 差距分析与增强路线图

下表是「让血缘图更全、更准、更可维护」的增强项，按性价比排序。标注了现状痛点与落点。P0 建议优先。

#增强项现状痛点方案要点 / 落点优先级
1跨来源实体消解升级目前仅靠 规范化 label + aliases 精确匹配去重；「采购订单/PO/purchase order」若无 alias 会分裂成多节点。在 mergeExtractionByLabel 前加一层候选归并：向量相似度（已有 EmbeddingClient）+ 编辑距离 + type 一致性，超阈值提示「疑似同一」由人确认或自动合并。落 ExtractionGraphMerger。P0
2列级血缘为一等公民血缘遍历只到表级/概念级；列级信息埋在 attributes.column / 边 label 文本里，不可查询。为属性建轻量「列节点」或在边上结构化 columnLineage:[{fromCol,toCol}]；LineageTraversalService 支持列粒度下钻。P1
3增量重建与图 diff 评审整库建图是全量重跑；新增一篇经验要全量重抽，且结果直接合并、无「变更预览」。按经验 content hash 缓存分批结果，只重抽变更批；建图产出与当前模型做 diff（新增/删除/改），前端评审后再合并。复用 useImportMerge/useImportDedup。P0
4约束冲突检测约束（cardinality/exclusive…）只存不校验；矛盾约束（A 既 exclusive 又 symmetric）无告警。已有 useConstraintConflicts 可扩展。落库/推演前跑一致性检查：基数矛盾、环形 depends_on、governs 指向不存在规则等，产出冲突清单。P1
5低置信复审队列inferred / 低 confidence 项混在图里，缺集中复审入口。建「待确认」视图：按 confidence 升序、source=inferred 优先，一键接受/驳回/改判；接受即升 confidence 并补 evidence。P1
6探索图片段字段增强⑤探索直采目前节点/边较「薄」（页面→process、对象→entity、associated_with 为主），缺 rel_type 细分与属性。结合本次探索改造新增的 tabs/statuses/links，在 buildGraphFragment 里补状态枚举→约束、页面跳转→flows_to/triggers，抬升结构化片段质量。P1
7建图质量评估指标无量化「建得好不好」；护栏是过程约束，缺结果度量。产出建图报告：证据覆盖率（derived 占比 × 有 evidence 占比）、悬空/自环剔除数、inferred 比例、孤点率、rel_type 分布、平均 confidence。落 ExperienceOntologyService.buildReplyText 旁的 metrics。P1
8规则可执行化type=rule 节点是自然语言；推演里靠 LLM 理解，无法机器校验实例数据是否违规。为规则补结构化表达（DSL/表达式 + 关联属性），结合⑩供血取数做「实例级违规检测」，让血缘图从描述走向治理。P2
9大图上下文可扩展性建图单次上限 500 篇；超大工作空间 skippedByCap 直接丢弃。分域建图（按经验 folder/tag 分子图）+ 子图间桥接边；或滚动窗口 + 已知实体持久回灌，突破单次上限。P2
10血缘可视化导出血缘结果主要在前端交互查看，缺可分享的静态产物。提供「血缘子图 → HTML/SVG/PNG 导出」，把 lineage 结果渲染成本文件这样的自包含报告，便于评审留档。P2
建议起步：P0 两项（跨来源实体消解 + 增量重建/图 diff 评审）直接决定「图能不能做全、能不能持续维护」，投入产出比最高，且都落在已有的 ExtractionGraphMerger / import 合并链路上，改动集中、风险可控。

15 · 术语表

术语释义
本体血缘图 / TBox概念级（非实例级）的业务语义有向图：节点=业务概念，边=受控语义关系。
derived / inferred来源标记：原文明述 vs 世界知识补全。决定 evidence 与 confidence 要求。
evidence≤30 字原文逐字摘录，节点/边的接地证据。
derived_tables / column概念/属性背后的物理表/列，连接语义层与物理层，实现表级图上的列级血缘。
供血 (feeding)为图节点绑定真实数据来源并取数；与「建图」解耦的第二阶段。
EXPLORE_GRAPH 片段探索智能体嵌在经验文档里的结构化 {nodes,edges}，建图时直接合并、免二次抽取。
加盐 (salt)导入时给 id 加时间戳前缀，避免多次导入/多模型间 id 碰撞。
known-entities 回灌把已识别实体清单塞给下一切片，让跨片的边能连上，防血缘断裂。
