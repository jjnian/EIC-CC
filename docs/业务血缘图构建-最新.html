业务血缘图构建 · 代码实现文档

本文完全依据当前代码（后端 com.tuiyan.backend 建图链路 + 前端合并/佐证/审核组件）梳理业务血缘图从经验库输入到可佐证、可审核、可实时观测的血缘图的完整构建过程：确定性血缘直出、LLM 分批抽取、三阶段命名统一、证据聚合、数据佐证与人工审核闭环。

总览：三段式范式

建图唯一入口是 ExperienceOntologyService（类注释明言「数据库 schema 直出图的旧链路已移除」）。数据流分三段：

① 沉淀：五类来源 → 经验库（Markdown 文档，origin: chat/upload/ddl/explore/websearch）
                     DDL 导出时确定性血缘已渲染成隐藏片段内嵌在文档里
② 建图：经验库 → 词表骨架 → 分域分批并行 LLM 抽取 → 归一/去重/对齐 → 跨批连边
                     → 结构化片段直连合并 → 图校验+证据聚合 → 加盐 → {nodes, edges}
③ 供血：图节点绑定真实库表/接口；推断边做值包含检验；低置信边进人工审核队列；
                     绑定升级为状态源，定时刷新节点态势

确定性优先

外键、视图定义、存储过程源码是数据库里现成的血缘 ground truth，正则/元数据级解析直出 confidence=1.0 的边，不让 LLM 重新猜。

LLM 只做语义

散文经验的实体/关系抽取、跨批关系补全、同义仲裁交给 LLM；其产出一律带来源与置信度标记，可被数据和人复核。

推断必须闭环

命名推断、跨批连边等低置信边不直接可信：值包含检验用真实数据升级/否决，审核队列交业务专家把关。

建图主流水线

核心方法 ExperienceOntologyService.extractFromWorkspace(...)（SSE 流式上报每步进度），按代码执行顺序：

1
读经验库 — 列出工作空间全部经验；文件夹名即业务领域（domain，无文件夹归「未分域」）；可按 experienceIds 圈定范围。
2
增量过滤 + 孤儿检测 — 增量模式按目标模型构建记录的内容哈希（SHA-256(title+content)）跳过未变化经验；检测「上次建图引用、现已删除」的孤儿来源，只报告不代删。
3
结构化片段直采 — 正文里 <!-- EXPLORE_GRAPH {json} --> 注释块（探索文档、DDL 确定性血缘共用同一标记）被解析成 {add_nodes,add_edges} 直连合并，并从正文剥离，LLM 不再重抽。
4
受控词表骨架 — 分域分层采样（标题+首段 300 字），一次 LLM 归纳「规范名+别名+类型」词表入库；增量复用、全量重建；失败降级为无骨架。
5
既有图回灌（仅增量） — 从目标模型检索与本批相关的既有概念注入 prompt，让新内容连回旧图，不在每次增量时断链。
6
域感知分批并行抽取 — 按领域分组、组内按 30k 字符预算打包（批不跨域）；DDL 批走 schema 专用 system prompt；4 线程并行、单批失败重试一次；批产出落 checkpoint 支持断点续跑。
7
服务端归一 + 批内去重 — LLM 对词表遵循不可靠，服务端把命中别名的 label 强制改写为规范名（normalize）；dedupeWithin 折叠批内同名重复；加批前缀 b0_/ex0_ 防 id 冲突；按 label(+aliases)+type 跨批合并。
8
向量兜底同义对齐 — 词表没收录的同义词（收款/回款）用 embedding 两两余弦召回 + LLM 批量仲裁 + 并查集折叠；发现的同义反哺词表。embedding 未配置整体 no-op。
9
跨批连边 — 并行各批互相看不见，跨批关系天然缺失；把实体清单（度数排序 + 分域轮转取样）+ 已有关系对喂给 LLM 只补跨批边，强制 source=inferred、置信度封顶 0.55、打 cross_batch 标记。
10
图校验 + 证据聚合 — sanitizeGraph 丢空 id/重复 id 节点、悬空边、自环；(from,to,rel_type) 重复边不是丢弃而是把证据聚合进 evidences，按独立证据数提置信（封顶 0.9）。
11
加盐 + 来源/领域兜底标记 — 全部 id 加 36 进制时间戳 salt 防多次导入冲突；derived_source/domain 空白处兜底回填。
12
产出 + 构建清单 — 返回 {nodes, edges, reply, salt, manifest, removedSources}；前端「合并进模型」前先跑结构体检，确认后回写 manifest 为构建记录，供下次增量。
两种落地方式：常规建图结果回传前端合并（POST /api/experiences/extract-ontology，SSE）；海量经验走 buildFullIntoNewModel 全量建图（expCap=MAX_VALUE），服务端直接落成新模型并回写构建记录，避免把万节点 payload 回传前端。

输入准备与增量建图

经验即输入

  • 单次建图默认上限 MAX_EXPERIENCES=500 篇，单篇正文截断 40,000 字符；超上限经验跳过并上报。
  • DDL 导出经验（origin=ddl）单独分批，用 SCHEMA_TO_ONTOLOGY_SYSTEM 专用抽取规则（映射确定、反幻觉更严）。
  • 用户额外提示（如「重点关注审批链路」）作为前缀注入每一批。

增量建图（内容哈希 manifest）

  • 目标模型必须存在且属于当前工作空间（防跨空间读构建记录）。
  • 哈希 = sha256(title + "\0" + content)；命中旧哈希 → 跳过；失败批的经验从 manifest 剔除，下次仍会重抽，不漏。
  • 孤儿来源（构建记录里有、经验库已删）持续提醒直到用户处理；其贡献的节点/边保留在图中，清理与否是用户决策。
  • 全部经验均未变化时直接报错提示「无需重建」，不空跑 LLM。

确定性血缘四通路（SchemaGraphFragmentRenderer）

数据源「导出结构到经验库」时，内省 schema 里的确定性血缘被渲染成结构化片段内嵌进 DDL 文档，建图时免 LLM 直连合并。只为「参与血缘的表/视图」建节点；表节点 label 优先取表注释（业务名）、表名作别名——让它与 LLM 抽出的同名业务实体自然折叠。

通路解析来源产出边source / confidence
① 外键内省元数据 ForeignKeyInfo子表 depends_on 父表（父=上游）derived / 1.0，evidence 带约束名
② 视图定义SchemaSqlLineage.viewFlows：视图 definition 包成 CREATE VIEW … AS 后解析 FROM/JOIN来源表 flows_to 视图derived / 1.0
③ 存储过程/函数SchemaSqlLineage.routineFlows：源码经 SqlLineageExtractor 语句级解析（INSERT…SELECT / CTAS / CREATE VIEW / MERGE / UPDATE…FROM）来源表 flows_to 写入目标表derived / 1.0，evidence 带过程名+语句类型
④ 隐式引用ImplicitRefInferencer 命名约定推断（生产库普遍不建 FK）子表 depends_on 父表（候选）inferred / 0.5，证据格式兼容值包含检验

SQL 语句级解析要点（SqlLineageExtractor）

  • 正则级而非完整 parser：只认「写入目标 + FROM/JOIN/USING 来源表」，表级粒度，列级映射交 LLM 语义补充；置信度 1.0、不会幻觉。
  • 先剥块注释/行注释/字符串字面量再按 ; 分句，防字符串里的关键字误报；CTE 名与函数调用（FROM unnest(…)）不算来源表。
  • 上限：单脚本 800 语句 / 500 条数据流；同 (源,目标) 去重保首条证据。
  • 该解析被两条建图路径共享（StructuralGraphService 与 DDL 经验片段），保证确定性血缘口径一致。

隐式引用推断规则（ImplicitRefInferencer）

  • 列名形如 xxx_id / xxxId / xxx_no / xxx_code / xxx_key（snake 与 camel 两套正则），前缀能对上某张表。
  • 表名匹配支持：复数（s/es/y→ies）、驼峰归一、剥 t_/tb_/tbl_/sys_/biz_ 常见修饰前缀。
  • 父表侧列选择：单列主键 > 与子列同名列 > 与后缀同名列（id/no/code），列必须真实存在，否则不产出——宁缺毋滥。
  • 已被声明 FK 覆盖的列、自引用（parent_id 型）一律跳过；单库上限 500 条防组合爆炸。
  • 证据按 child.col → parent.col 格式给出并带 derived_tables/derived_source，前端「一键数据佐证」可直接解析定位数据源验证。

命名统一三阶段（Schema-First）

大库分批抽取的根本矛盾：各批 LLM 独立看 30k 字，同一概念在不同批被叫成「客户/顾客/Customer」→ 假性重复节点、血缘链断裂。代码用三阶段解决：

① 受控词表

OntologyVocabService — 分域分层采样（每篇标题+首段 300 字，60~240 篇自适应），一次 LLM 归纳受控词表入库（每工作空间一份，上限 200 条）。preface 注入各批 prompt（控 token 只带 80 条）；LLM 遵循不可靠，服务端 normalize 再做确定性改写：命中别名 → 规范名、原名回填 aliases、空 type 补齐。

② 向量兜底对齐

EntityAlignmentService — 词表没收录的同义词在合并阶段兜底：全部节点 label 嵌入（上限 1200 个，按度数优先），两两余弦 ≥0.88 召回异名对（上限 150 对），交便宜模型一次批量保守仲裁，并查集折叠到高度数规范节点，重映射边端点。发现的同义映射反哺词表，下次走确定性快路径。

③ 既有图回灌

ExistingGraphContextService — 仅增量建图：embed 既有节点 label（上限 600，按度数），per-batch 用批文本向量检索 top-30 相关既有概念注入 prompt「请复用这些名字连接过去」；embedding 未配置回退注入度数最高的枢纽概念。失败返回空 context 不阻塞。

三阶段全部失败容忍：词表构建失败 → 无骨架建图；对齐失败 → 原图返回；回灌失败 → 不回灌。质量增强永不阻塞主流程。

分批并行与断点续跑

域感知分批

  • 先按领域（文件夹）分组、散文与 DDL 分开，组内按 BATCH_CHAR_BUDGET=30,000 字符贪心打包，批不跨域 → 抽取域内聚焦、每个节点/边可精确打 domain 标。
  • 非「未分域」批前缀领域聚焦提示，让 LLM 少漂到无关领域。
  • 专用有界线程池（MAX_PARALLEL_BATCHES=4，守护线程），后台线程手动透传 WorkspaceContext。

断点续跑（checkpoint）

  • 作业签名 = sha256(工作空间 + 模型 + configId + 缓存版本 v1)；换模型/prompt 版本自然隔离。
  • 批哈希覆盖「完整 LLM 输入 + 后处理决定因素」（序号/域/来源标题/preface/正文），命中即直接复用缓存产出，跳过 LLM 与后处理。
  • 成功一批落盘一批；失败批不缓存（重跑自动重试）；作业成功落库后清理，孤儿按 3 天 TTL 兜底清理。

部分失败语义

  • 单批失败自动重试一次；两次都失败该批记 null，用成功批次继续合并，SSE 上报「N/M 批失败，结果可能不完整」。
  • 全部批失败才抛错终止。失败批经验从 manifest 剔除，下次增量必重抽。

合并 · 跨批连边 · 图校验（ExtractionGraphMerger）

id 契约与按 label 合并

  • prefixChunkIds：各批内部 LLM 都用 n1/n2 命名，统一加批前缀（b0_n1）并同步重写边端点。
  • mergeExtractionByLabel：按标准化 label(+全部 aliases) 判等去重；同时看 type——同名但 type 明确不同（rule「风险」vs metric「风险」）不折叠，任一方 type 为空作通配。重复节点的 props/aliases 合并、边端点重映射。
  • dedupeWithin：用空图作基底走同一套折叠逻辑，兜住「单批内部重复」（词表归一把同批『顾客/客户』都改成『客户』的情形）。

跨批连边 pass

  • 批组取节点 id 前缀（b0_/b1_/ex0_），组数 <2 直接跳过。
  • 实体清单上限 500：按度数降序（枢纽承载跨批关系最多）+ 分域轮转取样（保证各领域枢纽都进清单，跨域血缘正是最缺、最有价值的）；已有关系对上限 800 防重复提出。
  • 服务端二次过滤：只收两端都在清单、且分属不同批组的边；强制 source=inferred、confidence 封顶 0.55、打 cross_batch 标记、重编 id。失败只记日志不影响主结果。

sanitizeGraph：校验 + 多源证据聚合

  • 丢弃：空 id / 重复 id 节点（保首个）、from/to 指向不存在节点的悬空边、自环。
  • (from,to,rel_type) 重复边 不是简单丢弃：重复往往是访谈/DDL/探索各说了一遍 = 多源互证。证据去重合并进 evidences（上限 6 条，evidence 保留首条兼容展示）；置信度取较高者，独立证据 >1 时每条 +0.1、封顶 0.9（确定性 1.0 不动）；来源取更强者（derived > manual > preset > inferred）。
  • 前端 evidenceMerge.ts 实现同一套规则——「合并进模型」遇到已有重复边时口径与后端一致。

血缘方向语义（EdgeSemantics ↔ useLineageTrace）

边的存储方向 from→to 由抽取映射规则决定，与数据流向不总一致。上下游遍历（LineageTraversalService BFS）按 rel_type 判定真实流向：

rel_type存储含义血缘流向
produces / transforms / flows_to / triggers / governs 及未知from=来源/施动正向 from→to
derived_from / composed_of / depends_on / consumesfrom=结果/依赖方/整体/消费方反向 to→from（上游源在 to 端）
associated_with纯关联不参与血缘遍历（可选 includeAssociations 纳入）
前后端各有一份该映射（后端 EdgeSemantics.REVERSED ↔ 前端 useLineageTrace 的 REVERSE_RELS / NON_LINEAGE_RELS），代码注释明确要求两处必须同步修改，否则后端 /lineage 遍历与画布血缘高亮会相互矛盾。

佐证与人工审核闭环

值包含检验（数据佐证）

  • 前端 lineageVerify.ts 从边 label/evidence 解析出 child.col ⊆ parent.col 四元组（兼容「a.col → b.col」与「naming:col↔parent.id」两种格式，配合 derived_tables 定位子表）。
  • 后端 POST /api/data-sources/{id}/verify-containment 在绑定库上验证子表列值是否都能在父表列找到（只读 SQL 白名单约束）。
  • 裁决写回：confirmed→0.95、likely→0.8、refuted→0.2；证据文本带匹配率与检验目标（可审计），hasVerification 防重复验证。

人工审核队列（ReviewQueueTab.vue）

  • 队列 = 置信度 < 0.7 的低置信 / 孤证推断边（LLM 猜的、没被数据或多来源佐证的关系）。
  • 确认：review_status=confirmed、置信度提至 0.9（专家点头 ≥ 多源佐证，仍低于确定性 1.0）、可附批注；否决：删边（走编辑器快照，可撤销）。

覆盖度审计（CoverageAuditTab.vue）

  • 把经验库（文件夹=领域，与建图口径一致）与图对照：每域节点/边规模、来源分布、推断占比、孤立聚集。
  • 缺口规则纯计算、不依赖 LLM、永远可复现：无经验支撑域 / 单一来源域 / 推断占比过高 / 证据覆盖低 → 生成调研任务清单，可导出《覆盖度审计报告》。完整性靠「收集→建图→找缺口→再收集」迭代。

供血绑定与实时态势

  • 图节点经 node_data_binding 绑定真实库表 / HTTP 接口（数据源为全局资源，工作空间按引用纳入）。
  • 状态源（NodeStateService）：绑定可配「状态查询（只读 SQL，首行首列为状态值）+ 阈值规则 + 刷新间隔」；采集失败不抛错，状态落为 error 级（态势图显示「探针失联」）。SQL 与取数供血同一套安全约束（只读白名单 + 危险函数黑名单 + 强制 LIMIT）。
  • 调度器（NodeStateScheduler）：独立小线程池（2 线程），每绑定最多一个任务、最小间隔 60s、活跃任务上限 50、连续失败 5 次自动停用；当前状态落 node_state，时序落 node_state_history（每绑定保留 500 条）。
  • 画布态势模式轮询 GET /api/node-bindings/states?modelId 按最严重级别着色——「建图是画世界，供血让世界活起来」。
